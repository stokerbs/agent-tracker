## 2. Proposed architecture

```
Browser (admin)
  └─ /studio/*  (Server Components + small Client islands)
       ├─ server actions  (zod → requireRole(admin) → RLS client → service client → logAudit)
       └─ lib/studio/ai/* (server-only)
             ├─ provider.ts        AiProvider interface (anthropic implemented; openai = honest "not configured")
             ├─ anthropic.ts       @anthropic-ai/sdk, structured outputs via zodOutputFormat
             ├─ prompts/*.ts       brand · thai-style · ideas · campaign · script · case-story · privacy · repurpose · creative-plan · knowledge-extraction · rewrite · fact-check
             ├─ actions/*.ts       generateIdeas, generateCampaign, generateHooks, generateScript, rewriteContent, repurposeContent, generateCTA, generateCreativePlan, extractCaseInsights, extractCustomerFAQs, runPrivacyCheck, recommendContentMix
             ├─ knowledge/search.ts  keyword search (pg_trgm/ilike + tags) — pgvector seam
             ├─ privacy/scrub.ts   deterministic PII detector (phones, plates, emails, LINE ids, addresses, names from a deny-list)
             └─ generation-log.ts  studio_ai_generations (ids only, never raw case PII)
Supabase Postgres (RLS: admin-only)  ·  Storage bucket `studio-assets` (foundation)
```

Key decisions
- **Admin-only V1.** RLS = `is_admin()` on every `studio_*` table. Supervisors/agents see nothing. Revisit when a content team exists.
- **One Content Master, many Variants.** Platform copies hang off a master; the calendar shows masters (with platform chips) by `scheduled_at`.
- **Sources are first-class rows** (`studio_content_sources`) pointing at knowledge / case-insight / customer-question / external / `ai_general`. The UI answers "AI เอาข้อมูลนี้มาจากไหน?" in one click.
- **Privacy gate before approval.** Deterministic scrub always runs at decision time; AI review adds nuance. Gate rule (`lib/studio/privacy/gate.ts`, shared by server and editor UI) = worst of (fresh scan, latest AI/human verdict). `approve` is refused while `blocked`; `review_required` needs an explicit human override recorded in `studio_content_reviews` (auto-recorded when `require_privacy_safe` is off). Text edits after approval demote the piece back to draft (`STUDIO_CONTENT_REOPEN`); schedule/publish re-scan and refuse `blocked`.
- **Minimum-context generation.** Only `approved_for_content` knowledge and `studio_case_insights` (already anonymized) reach prompts; never `studio_cases.situation/observations` raw and never ops `cases`.
- **No fake integrations.** Publishing, social APIs, video/image generation are 🚫 in V1 — the UI says so; the schema has the hooks (`published_url`, `studio_creative_assets`, `studio_analytics.source`).

## 6. AI architecture

- Provider abstraction: `getAiProvider()` → `{ generateStructured(schema, system, user, opts) }`. Anthropic implementation via `client.messages.parse` + `zodOutputFormat`. Model from `studio_settings.ai_model` → env `STUDIO_AI_MODEL` → `claude-opus-5`.
- Prompt modules compose: `brand` + `thai-style` (always) + task prompt. Knowledge context is appended as numbered `[K1]…` blocks so the model cites ids → become `studio_content_sources`.
- Every call logs to `studio_ai_generations` (refs + output, never raw case text). Failures are stored with `status='error'` and surfaced in the UI.
- Fact claims: the script generator returns `claims[]` with `source_ref` (K-id or `ai_general`) → mapped to `support_status` (`supported` if K-id resolves, else `ai_suggestion`).
- Privacy: `runPrivacyCheck` = deterministic scrub findings ∪ AI findings → status. Deterministic covers Thai/intl phone, email, plate (กข 1234 / 1กข 1234), LINE ids, URLs, house-number+ซอย/ถนน patterns, ID-card numbers, explicit dates, and names from `studio_settings.privacy_rules.denylist`.

## 9. Developer conventions (read before touching `/studio`)

- **Routes** live in `src/app/(dashboard)/studio/<module>/`. Route-specific components sit next to `page.tsx`. Shared studio UI lives in `src/components/studio/` (badges, source list, AI banner) — reuse, don't fork.
- **Auth.** Pages: `await requireRole(["admin"])` (layout already does this, pages may still call it). Server actions: `const profile = await requireStudioAdmin()` (throws) or `getStudioAdmin()` (returns null → `{ ok:false, error }`).
- **Data access.** Use the RLS client `createClient()` from `@/lib/supabase/server` for reads and writes — the admin role has full access via `is_admin()` policies. The service client is reserved for the AI layer / seed (server-only modules) — never in `"use server"` files.
- **Server actions** return `ActionResult<T>` (`{ ok:true, data } | { ok:false, error }`), validate input with zod, `logAudit()` sensitive mutations (approve/publish/privacy override/settings/knowledge approval), then `revalidatePath()`.
- **AI** is only called through `@/lib/studio/ai` (`generateScript`, `runPrivacyCheck`, …). Check `isAiAvailable()` in pages and render `<AiUnavailableBanner />` + disabled buttons when false. Show `RunResult.error` to the user; never swallow.
- **Approval gate.** `approve` must refuse when the latest `studio_privacy_checks.status === "blocked"`; `review_required` needs `approval_rules.allow_override` + a `studio_content_reviews` row with `decision = "override_privacy"`. If no privacy check exists yet, run the deterministic check first.
- **Copy** is Thai-first, hardcoded in components (matching `marketing-articles`), English technical terms allowed. Dates via `formatDate()` (en-GB), times `HH:mm` Asia/Bangkok.
- **States.** Every page: loading (`loading.tsx` or Skeleton), empty (`EmptyState`), error (`error.tsx`), AI-unavailable, privacy-review-required where relevant.
- **Tests.** Co-locate `*.test.ts` for pure helpers and for server actions (mock `@/lib/supabase/server` + `@/lib/studio/auth`, see `settings/security-actions.test.ts` for the pattern).
- **Do not edit** `src/lib/studio/types.ts`, `constants.ts`, `components/studio/badges.tsx`, `nav-config.ts`, `messages/*.json` without coordinating — other modules depend on them.

## 11. Bulk import of LINE OA chat history (offline)

Export chats from LINE Official Account Manager (CSV per chat: `ประเภทผู้ส่ง,ชื่อผู้ส่ง,วันส่ง,เวลาส่ง,ข้อความ`), put them in one folder, then on the Mac:

```bash
set -a; source .env.local; set +a
npx tsx --tsconfig tsconfig.scripts.json scripts/studio-import-line-history.ts ~/Downloads/line-history --dry-run   # parse + count only
npx tsx --tsconfig tsconfig.scripts.json scripts/studio-import-line-history.ts ~/Downloads/line-history --model claude-sonnet-5 --user <your profile uuid>
```

What it does per file: PII redaction per message (studio denylist + customer display names in the file, Thai digits normalised) → AI windows (~12k chars, `ลูกค้า:`/`นักสืบ:`) → `extractChatKnowledge` → writes **unapproved** rows: investigator knowledge (`tags: line-import, จากแชทจริง|ต้องยืนยัน`), case lessons (`category cases`, sensitivity confidential), service facts, and customer questions (`source import`). Customer claims are discarded; anything still carrying a high-severity identifier is dropped. Idempotent per file + window (`origin_ref = line-import:<sha1>:<n>`). Raw transcripts are never stored; the JSON report (counts only) is written next to the inputs. Review in `/studio/knowledge` (filter tag `line-import`) and approve what should feed AI content.

Measured on a 4-window pilot (Claude Opus 5, Sep 2026): ≈ 9.1k input + 5.5k output tokens and ~200 s per 12k-char window → ≈ US$0.18/window on Opus 5, ≈ US$0.07 on Sonnet 5 (output caps added afterwards should roughly halve that). The full 5-year export (6,009 chats → 2,505 with ≥ 2 customer messages → ~2,870 windows) is therefore ≈ US$100–200 on Sonnet 5 and several hours at `--concurrency 6`; pass `--model claude-sonnet-5` for bulk runs and keep Opus for content generation. Overlapping exports of the same chat (e.g. two Kimlank files) are deduped by content hash only when identical — import the longest export per chat.

Residual risk (documented on purpose): Thai has no word spaces, so person names are detected heuristically — formal titles (นาย/นาง/…), cue words (ชื่อ…/เรียกว่า) and a short word-bounded token after “คุณ”. A given name introduced without those cues can still reach the Anthropic API (processor, never stored raw) and is caught only by the customer-display-name/owner denylist, the prompt rules, the output re-scrub and human review before approval. Settings outages fail closed: capture, mining and import stop rather than run without the denylist.

## 12. Consolidation of imported knowledge (migrations 0115–0116)

Bulk import leaves thousands of overlapping rows. `scripts/studio-consolidate.ts [knowledge|questions|all] [--dry-run] [--passes 2] [--model claude-sonnet-5] [--user <uuid>] [--category a,b]` groups active rows per category (sorted by title, batches of 45) and asks the model for same-point groups; each group becomes one canonical row (`tags: line-import, consolidated`, `member_count`, still **unapproved**) and the members get `superseded_by`. Lists, counts and AI retrieval hide superseded rows (toggle "แสดงรายการที่ถูกรวมแล้ว"); the detail page shows the members of a canonical row and the canonical link on a member. Questions merge the same way with summed `frequency` and `member_count` (summed across passes). The unique `normalized_key` index is scoped to **active** rows (0116: `superseded_by IS NULL`); a collision merges into the existing active row, or is skipped (reported) when that row is already approved — mining/import lookups filter `superseded_by IS NULL` the same way so new hits land on the canonical row, never a hidden member. Canonical text is re-scrubbed: high-severity/denylist hits are dropped, softer findings add the `ต้องตรวจ privacy` tag; rows marked `restricted` are never sent to the model. Superseded members cannot be approved (toggle and edit actions refuse server-side; switch disabled); a member approved while a run is in flight is left untouched (supersede update is guarded). The CLI is a documented exception to per-row audit logging — traceability is via `origin_ref` + `studio_ai_generations` and are excluded from the source picker and global search. Deleting a canonical row re-activates its members (`ON DELETE SET NULL`). Sizing (2026-09-10): 6,840 knowledge rows → 157 batches, 4,609 questions → 77 batches per pass; two passes ≈ US$10–15 on Sonnet 5.

**Resilience (2026-09-11).** A home-network outage during a run failed 27 batches in a row, then killed the process when the strict settings load could not reach Supabase. Offline runs now pass `OFFLINE_RETRY` (`src/lib/studio/retry.ts`: 6 attempts, 5 s doubling to 120 s, 20 % jitter). Retried: the settings load (still fail-closed once attempts run out), page loads, supersede updates and the AI batch call via `runStructured({ retry })`. Transient means `fetch failed`, `Connection error`, DNS/connect/reset errors and HTTP 429/5xx/529. Never retried: credit balance, auth, truncated or schema-invalid model output, constraint violations, and timeouts on the billed AI call (the request may have run; the SDK already retries twice). Canonical inserts are not blindly repeated: a dropped response can hide a committed row, so a retry first looks it up (knowledge by a per-run, per-group `origin_ref`; questions by the single active `normalized_key` row carrying the written frequency and member count) and adopts it. The non-idempotent collision merge is never retried. After 3 consecutive batches fail transiently the run throws `ConsolidateAbortedError` and the CLI exits 2 with a resume hint; re-running is safe because only active rows are read. Transient AI failures no longer go to Sentry.

## 14. Publishing — Phase 2: auto-posting via Ayrshare (migration 0118)

**Goal.** From an approved/scheduled content piece the owner posts (now or at the scheduled time) to Facebook Page, Instagram, TikTok and YouTube through one aggregator, without our own Meta/TikTok app review. Owner decision 2026-09-10: pay for Ayrshare; start with FB · IG · TikTok · YouTube. LINE OA broadcast stays a later add-on (we already hold the token).

Missing key ⇒ honest "not configured" (buttons disabled + reason). The owner links the social accounts in the Ayrshare dashboard; Settings shows which are active (`/api/user`).

**Data.** `studio_social_posts` (one row per master × platform): provider post id/ref, `status queued|scheduled|published|failed|deleted`, `scheduled_at`, `published_at`, `post_url`, `error`, `caption_chars`, `media_asset_ids`. `studio_settings.social_connections` (0109) holds the last connection snapshot + per-platform defaults (YouTube visibility, TikTok privacy level).

**Gates (server, in order).** admin → rate limit (10 publish requests / hour) → master status `approved|scheduled` (same rule as manual publish) → schedule must be ≥ 1 min in the future when "ตามเวลาที่ตั้งไว้" → no live/queued post already exists for master × platform (`duplicate`; partial unique index 0119 guards the race) → linked accounts → fresh deterministic privacy scan of the exact caption per platform (strict_mode honoured) → platform requirements: Instagram needs ≥1 image/video, TikTok needs a video or 1–35 images, YouTube needs a video + title, Facebook may be text-only → assets must be `ready` and belong to the master → provider call → rows + `STUDIO_SOCIAL_POST` audit → master becomes `published` (immediate) or stays `scheduled` (Ayrshare holds the schedule). Caption per platform = the platform variant's caption if present, else master caption + CTA, truncated to platform limits (IG 2,200 · TikTok 2,200 · YouTube title 100 / description 5,000 · FB 63,206). Captions for the aggregator platforms drop the `@` of handles (`stripMentions`): Ayrshare rejects a post with error 159 when the same @mention was already used that day, and nearly every caption ends with "LINE @detectivepluse" (found 2026-09-11 after four rejected requests). Emails, URLs and LINE OA captions keep the `@`. The publish privacy scan reads both the posted caption and its pre-strip source (`captionSource`), so a stranger's handle is still caught. Our own handle is allowlisted with or without the `@`. YouTube posts also scan the title and hook. Platforms with different captions go out as separate aggregator requests so each receives exactly the previewed text; a group that the provider rejects becomes `failed` rows while the others proceed.

**Sync.** Cron `/api/cron/studio-social-sync` every 30 min: for rows `queued|scheduled`, ask Ayrshare `/api/history/:id` → mark `published` (post_url) / `failed` (error) and flip the master to `published` once every platform row is published; owner gets a LINE push on the first failure. Deleting a post calls Ayrshare `DELETE /api/post` and marks the row `deleted`.

**Reconciliation after an ambiguous failure (2026-09-14).** On 2026-09-14 an Ayrshare `POST /post` timed out at 60 s while the post had in fact gone live on all three platforms — our client reported `rejected`, wrote no rows, and the owner had a live post the studio knew nothing about (repaired by hand). A provider rejection is still a real "no"; anything else (timeout, dropped connection) is now treated as unknown: `publishMaster` asks `findRecentPostByRef` (Ayrshare `GET /api/history?lastRecords=25`) for a record whose `notes` equals the master id, whose platform set is exactly that request's group, and which was created inside the attempt window (60 s of clock slack). Only an explicit `success` carrying per-platform results counts as posted; anything still in flight comes back as not-yet-published so the sync cron keeps following it, and a status we do not understand (including `deleted`) is refused. A provider post another row already owns is never claimed a second time, so the owner's delete button cannot end up pointing at someone else's post. A match is used as the provider's answer — rows, urls and the master flip all follow as usual, with `provider_recovered: true` in the audit metadata (the autopilot sweep's own recovery is a separate `swept_from` key) — and a miss, an errored record or a failed lookup leaves the original failure standing. Known limit: the lookup reads the last 25 records, so an account posting very heavily in that minute could miss its own record and simply fall back to the old behaviour.

## 15. Video — Phase 3: template short-video rendering (migration 0120)

**Goal.** Turn a content piece into a vertical short video without a video-generation model: per-shot image (already generated in Phase 1) + per-shot Thai voice-over (ElevenLabs) + hook overlay + burned-in subtitles, rendered with ffmpeg into 1080×1920 H.264/AAC. Output is a `video` asset that Phase 2 can post to TikTok / Reels / YouTube Shorts.

**Why ffmpeg-static, not a video model or Remotion.** Deterministic, cheap (only TTS costs), no Chromium, no third-party render farm. `ffmpeg-static` ships a Linux binary (~45 MB, libass + freetype + libx264) that fits Vercel's 5 GB function limit; the route handler declares `maxDuration = 300`. Thai subtitles use libass (ASS file) with the bundled OFL font **Sarabun** (`src/lib/studio/video/fonts`), because libass shapes Thai combining marks correctly where `drawtext` does not. The filter is `ass=…:shaping=complex`: with the default "auto" the macOS ffmpeg-static build shapes simply and draws a tone mark over the upper vowel (ที่ reads ที, เรื่อง reads เรือง). The Linux binary Vercel runs was checked in Docker and shapes correctly either way. The hook card uses libass BorderStyle 4 (one box per event) with a transparent outline, because BorderStyle 3 boxes each glyph and left a notch under stacked marks.

**Timeline.** `creative_plan.shots[]` drive the cut: each shot's `voice` text is synthesised separately (mp3 128 kbps CBR, duration derived from bytes) so the shot lasts exactly its narration + 0.35 s pad; its image is the asset the owner generated for that shot (`meta.target = {kind:"scene", index}`), else the cover, else any image. A punch-in zoom on every still (template v2, below). Shot 1 shows the hook as a large overlay for its first 2.5 s. Subtitles: lines break at spaces first (Thai phrase boundaries), so every original space survives as a space or a line break; a phrase is split internally only when it is wider than its line ceiling (40 graphemes by default, 30 for captions), into parts of balanced width at ICU word boundaries, preferring the spot just before a clause opener (และ แต่ ว่า ซึ่ง …). Never before ๆ, closing punctuation or a handle. Widths are measured in graphemes because stacked Thai marks take no width. Captions show one line at a time (template v2, below), libass auto-wrap is off (WrapStyle 2), and cues are timed by visible width. Because nothing wraps automatically, the hook overlay goes through the same breaker with narrower lines (14 target / 30 max graphemes at 88 px). Segment widths are summed as they accumulate, so long inputs stay linear. The first version dropped spaces and cut words such as หลักฐาน and แต่ละ, found on real clips (2026-09-11). Per-shot audio is cached as `audio` assets keyed by `meta.shot_hash` (text + voice id) so re-renders don't pay TTS twice.

**Template v2 "viral" (2026-09-11).** The owner picked this style over "noir" and "cctv" prototypes rendered from a real clip. Settings and the autopilot use it for every render; assets record `model: template-v2`, `meta.style: viral`.
- Motion: each shot punches in (1.12× in 0.5 s, then a slow creep) and odd shots drift sideways. Shots change with rotating xfade transitions (slideleft, zoomin, slideup, smoothleft, circleopen), 0.25 s each. Every shot but the last is padded by the transition length and each transition starts where the next narration starts, so audio stays aligned.
- Look: a light grade (saturation 1.18, contrast 1.06), a yellow progress bar across the top and a small DETECTIVE PULSE tag under it.
- Captions: one line at a time (`captionChunks`, 14 target / 30 max graphemes, Sarabun Bold 92 with a heavy outline) at y 1230, popping in, with numbers and `EMPHASIS_WORDS` in yellow. Highlights match whole ICU words, joining up to three and preferring the longest, so ลับ inside กลับ or จริง inside จริงจัง is never coloured. The 30-grapheme ceiling is deliberate: a shorter one makes the breaker split more phrases on ICU word boundaries, and ICU over-splits compounds (หลัก|ฐาน, ลงพื้น|ที่).
- Hook: a yellow card that slams in for 2.5 s.
- Gotcha: any ASS `Spacing` on a style that renders Thai makes libass drop tone marks, so only the Latin tag uses letter spacing.
- Cost: a 75 s clip renders in about 21 s locally. On one vCPU (Docker linux/arm64 `--cpus=1`) the first 20 s took 42 s with v1, 34 s with the first v2 settings and 27 s after moving zoompan to a 1.5x canvas with x264 `superfast`; a full 75 s clip at the first settings took 216 s and a 24-shot 180 s clip 353 s, so very long manual renders can still hit the 240 s ffmpeg timeout (autopilot clips are about 30 s). The Linux binary was checked in Docker for every transition, the bar overlay and the styled captions.

**Storyteller format (2026-09-11).** The owner asked for a "person telling the story" clip and picked "นักสืบนิรนามในเงามืด" (anonymous detective in shadow) over a Veo talking head, a HeyGen/D-ID avatar or self-recorded footage.
- Presenter image: image target `presenter` (Media section, or the button in the video section) generates a fixed-prompt backlit silhouette (`PRESENTER_SCENE`) that already satisfies the no-face safety negatives. It is stored per master as kind `image` with `meta.target.kind = "presenter"`; the template format never uses it.
- Shots (`resolveShotImages(plan, images, { format: "storyteller" })`): the presenter opens, closes and carries every other shot; the shots between cut away to that scene's image, else the cover. Each shot carries `role` presenter or broll.
- Render (`job.params.format`): fade transitions (0.35 s), a slow centred push-in on presenter shots and the viral punch-in on b-roll, a yellow audio waveform (`showwaves`) over presenter shots only, and a slide-in name card "นักสืบนิรนาม / DETECTIVE PULSE" on the first presenter shot after the hook. Captions, hook card and progress bar are the viral ones. Assets record `meta.format` and `meta.style: storyteller`.
- Editor: a format toggle next to "สร้างวิดีโอ"; `createRenderJob({ masterId, format })` re-checks the presenter server-side with the same resolver.
- Autopilot: `video_format` template | storyteller | alternate (flips from the last done/review run's `stats.format`). Storyteller generates the presenter image after the cover; if that fails or time is short the run falls back to template and records `stats.format_fallback`.

**Job model.** `studio_render_jobs` (status `queued|running|done|failed`, `step`, `progress`, `error`, `asset_id`, `params`). The editor creates a job (server action, admin + master not privacy-blocked) and then POSTs to `/api/studio/render/[jobId]` (route handler, admin session, `maxDuration 300`) which runs the pipeline and updates the job; the UI polls `getRenderJob` every 3 s. Concurrency: one running job per master. Output mp4 → bucket `studio-media` (mime allowlist gains `video/mp4`, size limit 200 MB) → `studio_creative_assets` row kind `video` with duration/dimensions.

**Gates.** admin → master exists and status not `archived` → fresh deterministic privacy scan (hook/script/caption) not blocked → plan has ≥ 1 shot with voice text → ≥ 1 ready image asset → TTS + ffmpeg configured. Costs: TTS only (≈ ฿3–10 per minute of narration); render is CPU time on Vercel.

**Honest limits.** No B-roll motion video (stills with zoom), no music (licensing), one aspect (9:16) in V1, ffmpeg wall-time on a 1 vCPU function ≈ 1–2× the video length; a 60 s clip may take ~2 min. Not browser-verified with an owner session; the pipeline is exercised end-to-end locally with the real providers before merge.

## 15b. Bulk approval of consolidated knowledge

**Whose name (2026-09-25).** The rule added on 2026-09-15 to catch "ชื่อของลูกค้า สมชาย" took any text between the particle and the name, so it read "ลูกค้าถือ**ชื่อที่ไม่แน่ใจว่า**ใช่หรือเปล่า" as an introduction — and held a finished clip for owner review on 2026-09-24 while the AI reviewer, in the same record, wrote that the scanner had got it wrong. Nobody was watching the queue, so nothing posted that week. The first attempt at a fix required a word saying *whose* name it is, and the security gate measured what that cost: Thai writes "whose" **in front of** ชื่อ at least as often as behind it (ลูกค้าชื่อ สมชาย, พยานชื่อ สมหญิง), and the list of whose-words cannot be closed — every kind of case brings a new one (คนหาย, ผู้เช่า, เจ้าหนี้, ทายาท, ชู้). So the rule enumerates the other side instead: the **name slot**. `NOT_A_NAME` is the field labels and grammar words that are never a person (ที่อยู่, นามสกุล, เบอร์, อายุ, ที่, ไม่, การ…), a gap that says the name is unknown (ไม่แน่ใจ, ไม่ตรง, สะกด) is not an introduction, and on the spaced form a field word in the gap means the sentence is listing fields rather than naming anyone. Hedging alone decides nothing: "ชื่อที่สงสัยว่าเป็นสมชาย" identifies someone and "จำไม่ได้ว่าสมชายหรือสมชัย" holds two real names. A sentence is dropped only when the gap hedges (`HEDGE`) **and** what follows is a judgement about a name rather than a person (`PREDICATE`: เป็นคนเดียวกัน, ถูกต้อง, ครบทุก, หรือเปล่า…) — whole phrases, because a prefix list has twice taken real names with it here. `NOT_A_CUE` keeps ชื่อเสียง/ชื่อบัญชี out of both rules — "รักษาชื่อเสียงของลูกค้า" is this brand's own copy — and ชื่อเล่น takes the same particles as ชื่อ, since a nickname is full PII and the rows write "ชื่อเล่นของเป้าหมายคือ…" constantly.

Known gaps, measured rather than guessed. `NOT_A_NAME` matches a prefix, so every token in it costs the names that start with it: การ, จะ, ต้อง and ทีม stay (they earn their place against real false positives) and take การุณ, จะเด็ด, ต้องตา and ทีม with them; the thirteen measured as earning nothing (with เลขที่, เลขคดี, ตรงกับ and ตรงกัน added back as whole phrases, which is what those prefixes were really for) (ตาม, จาก, เป็น, ครบ, ถูก, ผิด, ยัง, เต็ม, จริง, เลข, รูป, ตรง, and แพ็ narrowed to แพ็ก) are gone — those four were costing เลขา, ตรงใจ, แพ็ท and แพ็ตตี้ while เลขบัตร, รูปถ่าย and แพ็ก already covered what they were for. A form dump — "ชื่อ นามสกุล สมชาย ใจดี" — is not detected: the field label stops the scan rather than being skipped, and every attempt to skip it brought back worse false positives. ชื่อจริง stays a compound, so a person actually called จริงใจ is missed. A name with no cue at all ("จำไม่ได้ว่าสมชายหรือธนวัฒน์") is not caught by any rule here, on main or now. `ชื่อ<slot word>คือ<name>` is silent for all 45 slot words: right for the field labels, wrong for พยาน, which in this business names a person — kept because the label sense is the common one in the rows. The compensating controls for all of these are the owner denylist (high severity) and the AI privacy pass, which may only make a verdict stricter. **Numbers glued to Thai words (2026-09-26).** The same no-spaces property that broke the name rules had been hiding licence plates all along, on main and every revision before it: `PLATE_RE` ends on a lookahead that refuses Thai letters, so "ทะเบียน กข 1234จอดอยู่หน้าบ้าน" produced no finding at all and the plate was stored and publishable. That boundary cannot simply be relaxed — two bare Thai consonants and a number is an everyday phrase, and relaxing it read "รอ 5นาที", "ขอ 2ชุด", "คน 3คน" and five more of nineteen ordinary sentences as plates, each of which would hold a finished clip in the review queue. So the strict rule keeps its boundary for uncued text, and a **cue** carries the glued form instead.

The cues come in two tiers, because they are not equally trustworthy. ทะเบียน, ป้ายทะเบียน, ทะเบียนรถ and ป้าย are strong: after one of them, consonants-then-digits is not a quantity, and one digit is enough. รถ is weak — Thai glues it onto the front of ordinary words, and treated like the others it read "รถชน 3 ครั้ง", "รถวน 2 รอบ", "รถผม 2 คัน" and "ซื้อรถ งบ 5 แสน" as plates — so it needs a space after it and two digits in the plate. The shorter cues also refuse to be followed by รถ: without that, the engine backtracks into ทะเบียน and reads the รถ of "ทะเบียนรถ" as the plate's own letters, which stored "กข 12345" beside a token saying the plate was gone. After a cue the floor is one consonant and one digit but not both — "รถ ก 1 คัน" is a count, and the uncued rule's two-digit floor would lose real single-digit plates.

Measured on the QA gate's 490-row grid, which varies the one dimension mine did not — whether the cue is glued to the plate or separated from it — the digits were readable in 290 rows before and 42 now, with no row carrying a misleading token. All 42 belong to the weak cue: 35 where รถ is glued straight onto the plate ("รถกข 1234จอดอยู่") and 7 where it carries a single-digit plate ("รถ ญฐ 7"). The first group is the price of that space, and it is not a small one — the gate measured the alternative too: allowing รถ to glue recovers those and produces 17 false positives of the form "รถผม 20 ปีแล้ว", "รถชน 30 ครั้ง", "รถทน 20 ปี", which are the same shape letter for letter as a plate. ทะเบียน catches both groups when a customer names the plate that way, which is the common case. Ordinary sentences using those cue words in their everyday sense — 33 of them, including "ทะเบียนบ้าน เลขที่ 12", "ป้ายราคา 500บาท", "รถมือ 2" — produce no new finding, and neither does this brand's own published copy.

**The lane rule was attempted twice and withdrawn.** `ADDRESS_RE` expects the house number before the lane, so "ซอย 5" — the order people use when they give a lane without a number — goes unflagged even beside a matched "เลขที่ 12/3". A pattern for ซอย / ซ. / ถนน / ถ. / หมู่ followed by a number catches it, and cost more than it was worth in two successive forms. Flagging the shape outright read 14 of 16 ordinary sentences as high-severity addresses ("ตามรถบนถนน 3 ชั่วโมง", "แบ่งทีมเป็นหมู่ 2 ชุด") and moved 9 of 14 plausible captions from safe to blocked. Requiring a postal word within eight characters looked like the answer — the measured gap is 1–6 in real addresses against 13–26 in narration — but the QA gate then generated the shape systematically, place word × lane word × unit word, and **240 of 240 rows were false positives**, because Thai puts a place word next to a clause about a road as readily as next to an address ("หมู่บ้านนี้ ถนน 4 เลนกว้างมาก"). Distance is not the distinguishing feature.

What the measurements point at, for whoever takes it next: the token **after** the number. เลน, เมตร, ชั่วโมง, กลุ่ม, ชุด, อย่าง, ข้าง, สาย, คัน, นาที are measurements, and a real address never has one there. That is the one approach not yet tried, and it is its own change with its own gate rounds — the acceptance criterion the QA gate has already stated is 0 high findings on that 240-row product set with no loss against nine real address shapes. Narrowing the pattern to ซอย / ซ. alone was also measured: 1 of 12 false positives but 3 of 9 real shapes lost, since Thai roads are named rather than numbered ("ถ.พระราม 2" is an address this rule never catches anyway).

Anchoring cost one class outright before it was caught, and it is worth recording why the same idiom is safe on the email pattern and not here. On an email, starting the match further left always succeeds, so the anchor only forces it to the left edge of a run — nothing changes. A house number has to begin with a digit, so in "อาคารเอ-88/8 ซ.ลาดพร้าว 5" the `-` cannot start a match and the `8` is refused by the anchor: no position can start at all, and the whole address went unflagged. The security gate measured 454 rows of an 11,008-row fuzz disappearing that way, including ordinary Thai forms like "ยูนิต A-12/3 ซอย 7". The leading `[\/-]?` restores them at no measured cost — still 2.6 ms per 100,000 characters — and they are pinned by tests with their exact excerpts. What stays silent is two separators before the number ("//99", "--99"), 17 rows of that fuzz, and a space **before** a separator, "99 /12ซอย", which the old form only half-caught (it matched from the second number and redacted part of it) — 392 rows.

The email anchor changes no match in the flagged/not-flagged sense — measured on a 400,000-string fuzz with nothing lost and nothing newly flagged — but it does narrow a span in one family: a second address whose local part starts with `_`, `%`, `+` or `-` glued straight onto the first one's domain, "somchai@gmail.com_tag@hotmail.com". The field is still blocked, because an email is high severity, but `redactForInbox` would leave `_tag@hotmail.com` in the stored row beside an `[อีเมล]` token, which is the misleading-row shape this file keeps warning about. 8 of 4,511 fuzz cases, and nobody writes two addresses with no space between them.

What is still silent, each pinned by a test or listed here rather than implied: a plate with **no** cue whose digits run into the next word ("เห็น กข 1234จอดอยู่" — the alternative was those eight false positives); the weak cue with a single-digit plate; a cue separated from the plate by anything but whitespace ("ทะเบียน: กข 1234จอดอยู่", "ทะเบียนคือ กข 1234", "ทะเบียน-กข 1234", "รถสีขาว กข 1234"); "ทะเบียน กข.1234" with a dot as the separator; and a lane number with no postal word within eight characters of it — "อยู่ ซอย 7 ครับ", and also two real address shapes where a phrase intervenes: "หมู่บ้านกลางเมือง หมู่ 5" (gap 10) and "ที่อยู่ปัจจุบันของเป้าหมาย ซอย 7" (gap 18). Eight is deliberately well inside the measured separation (6 against 13) rather than at its midpoint, because the cost of the other direction is a blocked clip. Proximity is a heuristic and it can also over-flag when a postal word happens to land next to narration — "คดีนี้อยู่อำเภอเมือง ถนน 4 เลนกว้างมาก", 1 of 10 in the gate's set — which is fail-closed. The other identifiers were checked at the same time: a phone number, a Thai ID, a date and an email all end on a digit or character boundary, so Thai text after them is harmless — **but an age does not**, "เขา 34ปีแล้ว" and "ลูก 5ขวบครับ" are silent unless the word อายุ is present, which is low severity and older than this work.

Two things found while measuring this and left for their own change, both identical on main. **Thai digits are invisible outside the inbox**: `normalizeThaiDigits` runs in `redactForInbox` only, so `scrubText` called from publishing, rendering, consolidation and history import sees "ทะเบียน กข ๑๒๓๔", "โทร ๐๘๑๒๓๔๕๖๗๘" and "เลขบัตร ๑๒๓๔๕๖๗๘๙๐๑๒๓" as clean text. **`ADDRESS_RE` backtracked superlinearly, and now does not (2026-09-26).** Its house number was written `\d+[\/\d-]*`, where both halves match digits, so the engine can split a digit run between them in exponentially many ways. A long run of **plain** digits followed by a Thai letter — no match, maximum backtracking — cost 4.7 s at 1,600 digits and 584 s at 8,000, measured on the pattern alone; the same run with a `/` or `-` in it stays at 15 ms, which is why one gate could not reproduce what the other measured. It was reachable from the LINE webhook, where `captureCustomerMessage` is awaited before LINE gets its answer: one 1,491-character message held the handler for 3,685 ms. The inbox's own 1,500-character cap bounded that; it did not prevent it.

The number is now `(?<![\d\/-])\d+(?:[\/-]+\d+)*[\/-]*`, and each part was measured rather than chosen. Writing the separators as their own group removes the ambiguity, but on its own it is still quadratic — the scan restarts at every digit — at 1.3 s for 20,000 digits and 37 s for 100,000. The lookbehind is what makes it linear, 1.9 ms at 100,000, by refusing to start in the middle of a run. And the `+` on the separators with a trailing `[\/-]*` matters for recall, not speed: a stricter form silently stopped flagging house numbers typed with a separator left hanging — "99/ ซอยอารีย์ 2", "45- ถนนสุขุมวิท", "12// หมู่ 3" — which the QA gate measured at 1,560 rows of a 10,643-row set, every one of them going from a redacted address to no finding at all. The first version of this fix claimed to find "the same addresses" and did not; both gates caught the claim.

Through `scrubText`: 3,000 digits went from 31.6 s to 5.9 ms, and the webhook message from 3,600 ms to 5.7 ms. Two tests hold it: the 1,600-digit case must finish inside 250 ms, and doubling the input must not multiply the work by more than five — the old form grew 8× per doubling, the quadratic middle version 4×, this one about 1.2×. A budget alone would only have pinned "not catastrophic".

`scrubText` also caps what it reads at 20,000 characters per field, because nothing outside the inbox capped anything — publishing, rendering, consolidation and history import hand it whole documents, so any pathological pattern in here had no bound at all. Truncation is not silent: the tail was never read, so a field longer than the cap produces a high-severity finding of its own and the gate cannot call the piece safe. `EMAIL_RE` got the same treatment, because the QA gate profiled every pattern in the file at the sizes the cap allows and found it was the one still costing anything: its local part was retried from every character of a long alphanumeric run with no `@` in it — 163 ms at 16,000 characters, 2.7 s at 65,000 — and the same lookbehind makes that 0.1 ms and 0.3 ms, with no match difference across fourteen shapes including "..a@b.com", "-a@b.com" and "1234a@b.com". An earlier version of this section named `PHONE_RE` and `AGE_RE` as the slow ones; the gate could not reproduce that and neither could I — both are flat at 0.04 ms — so the next person would have gone looking in the wrong place.

The cap is 20,000 because a script is validated at exactly that (`content/actions.ts`), so that length has to pass and one character more must not; there is a test on both sides of the boundary. A **caption** is validated at 65,000, though, and Facebook's own limit is 63,206, so a caption between those two numbers saves normally and is then blocked at publish and at render with a length reason rather than a PII one. That is fail-closed rather than a leak, and it is the mismatch to settle next — now a free choice rather than a blocked one, since nothing in the file is superlinear any more: either bring the caption ceiling down to what a caption really is, or raise this cap to cover it.

The performance is held by a test at the cap rather than at a token size: a 20,000-character field of digits and one of alphanumerics must each scan in under 300 ms, where the unanchored house number costs about 2,160 ms and the unanchored email about 255 ms. A budget at 1,600 characters, which is what this PR shipped first, could not see the quadratic form at all — it cost 14 ms there. The scale-free assertion stays alongside it.

Truncation is logged as well as reported, because a quiet drop in scan coverage on the server is exactly what this module's other warning exists for; the line carries the field name and its length, no content.

**Where the name is (2026-09-26).** Five builds of the LINE inbox redaction tried to work out which token inside a name finding was the name, and each one shipped rows that kept the name and gained a `[ชื่อ]` reading as redacted — worse than an obvious miss, because a person or a later step believes it. The gates measured the guessing at up to 100% leakage in the commonest shape, and each fix moved the blind spot rather than closing it. The rule that matched is the only thing that knows where the name is, so it now says: `PrivacyFinding.name` carries the name slot, and everything downstream uses it instead of re-reading the excerpt. A rule that cannot say — the spaced introduction, where "ชื่อของ ก ข" is a label and a name in one reading and a name and a word of the question in the other — omits it, and a finding without it is redacted whole.

What that took in the rules themselves:

- every name rule captures its name slot, and the `ชื่อของ … คือ` form captures a following second token too, since a Thai full name is two and the surname would otherwise sit beside the token.
- the spaced introduction stops its gap at a particle after a space, so the slot lands on the name rather than on the question behind it, and has a second alternative that steps over exactly one particle — because customers press Enter and write the label, a particle, then the name ("ชื่อของเป้าหมาย ครับ\nสมชาย"), and `redactForInbox` normalises the newline to a space. The tight alternative is tried first, so the short reading wins and the question survives.
- particles and cues cannot be tested as bare prefixes. เจ้าหนี้ contains จ้า, มะนาว contains นะ, and ผู้ว่าจ้าง contains ว่า; each of those blocked a real name in measurement, the same trap `NOT_A_NAME` pays for with การุณ and จะเด็ด. So a particle counts only after a space, a particle in the slot must be the whole slot (which keeps คะนอง a name), and ว่า is a cue only outside ผู้ว่า.
- the inbox redacts in one pass over spans computed on the original text. Doing it finding by finding let a wide name finding erase the text a plate finding was still waiting to match (the row kept the digits), and doing identifiers first let the name pass eat a token that had just been inserted. A **name** span extends to the end of the word, because a name slot stops at ten letters and Thai writes no space inside a word; an identifier span does not, since a phone number, a plate or an age ends where its pattern ends and extending those merely ate the sentence behind them ("อายุ 34 ปีที่แล้วเขาหายไปจากบ้าน" became a single token).

Measured against the security gate's own corpus (7,614 rows, twenty shapes) and sixteen hand-written multi-line messages: a name is readable in 1,584 rows against 6,769 on main, and **2 rows carry a misleading token, against 296 on main**; on the multi-line messages, 0 leaks and 0 misleading against main's 12 and 1. On a second corpus of 6,048 rows: 168 leaks against 4,699, no misleading rows against 702, no orphan syllables, and 1,401 rows keep the customer's question where main kept none.

A name the rule reports is redacted at **every** mention in the message, not only inside the finding that reported it — naming the target and then talking about them ("ชื่อของลูกค้าคือ สมชาย ครับ สมชายหายไป 3 วัน") is the most natural way to write one of these messages, and both gates found that redacting the first mention only left the name in the row beside a token saying it was gone. The first token of a full name is searched too, since the later mention is usually the first name alone. The token after a name goes with it, because a Thai surname alone identifies a family and reads as redacted when a `[ชื่อ]` sits in front of it; only the `คือ` rule can report that second token itself, since extending the others read "นางสาวสมหญิง ทำงานที่นั่น" as a full name. What counts as "not a surname" is one shared list, used by the rules and by the inbox — two copies drifted to sixteen and twenty-seven words and disagreed about which surnames to keep — and a word on it counts only as the **whole token**. As a prefix it kept มีชัย, มีสุข, ที่รักษ์, ช่วยชาติ and อยู่สุข readable beside the token: the prefix trap this file has now paid for three times. A run that **ends** in a question or discourse word, optionally with a politeness particle after it, is the customer speaking rather than a surname, because Thai glues a clause into one run and would otherwise lose it whole ("ชื่อเล่นว่าเอ ขอเอกสารด้วยครับ" lost everything after the name). The test is at the end because that is where the language puts those words, while a surname ends on an auspicious syllable — ชัย, ศักดิ์, รัตน์, ทอง, สุข. Testing for them anywhere inside the run was a veto that failed **open**: นะ is a syllable in ชนะชัย, ธนะรัตน์, มานะชัย and จิตรชนะ, one of the commonest families of Thai surnames, and the security gate measured 80 of 280 surname shapes surviving beside a token. A particle **alone** does not mark speech, because Thai glues one onto a surname as readily as onto a question: reading the ครับ in "นายสมชาย ใจดีครับ" as speech kept the surname in 168 of 168 measured rows beside a token saying the name was gone. What is left ambiguous is a surname glued to a discourse word — "ใจดีด้วย", "ใจดีเลย", "ใจดีไหม" — which stays, measured at 168 rows of a six-tail grid. Dropping ด้วย and เลย from the list would close it and cost the commonest polite request in these rows ("ขอเอกสารด้วยครับ"), which is not a trade worth making. Measured on 28 real surname shapes across all four rules: readable 28 on main → 0, misleading 25 → 0. A nickname of two or three letters is redacted even where it sits inside another word, so "ขอเอกสารด้วย" loses its เอ. Skipping those kept บอย readable in "ผมหาบอยไม่เจอเลย" beside a token saying it was gone, and that is the rule both gates hold and this design is built on: **when it is ambiguous, redact**. An over-redacted row costs the mining layer a question; a row that looks redacted and is not costs a customer their name. When the next word is not a surname, the row loses one word of the question — the cheaper way to be wrong in a store of customer PII.

Measured across both gates' corpora — 7,614 generated rows in twenty shapes, sixteen hand-written multi-line messages, and a repeated-mention set: in a message that names **one** person, no row carries a misleading token (296 on main), a name is readable in 1,582 rows against 6,769, and a property sweep over 3,535 reported names finds none of them surviving anywhere in the stored row.

That claim stops at one name, and the scope matters. When a message names two people and one of them is written in the glued shape below, the row gets a token for the name the rules can see and keeps the one they cannot: measured on 100 such rows, the second name is readable in 80 against 75 on main, and 80 carry a token against 45. This is the glued gap showing through rather than a second defect — the rules never see that name, on main or here — but it is the one place where "a `[ชื่อ]` means the name is gone" is false, and it is false more often than on main precisely because more first names are now caught. Where both names are in shapes the rules see, both go.

On ordinary questions that merely contain the word ชื่อ, 4 of 40 are altered against 2 on main, and 3 of those lose the whole message to a single token where main lost none: "ชื่อในระบบสะกดผิด แก้ได้ไหมครับ", "ชื่อที่สะกดผิดในรายงาน แก้ไขได้ไหม", "ชื่อในระบบกับในบัตรไม่ตรงกัน ทำไงดี". The scanner's finding on those is identical on main, which simply declined to act on it.

Three known gaps stay, each measured rather than guessed. **A label glued to the name** ("ชื่อของลูกค้าสมชาย ครับ", and the same with no space at all) has no separator, so no rule can say which token is the name and **none of them flag it at all** — this is invisible to the publish gate too, not only to the inbox, and the message is stored as written, exactly as on main. It is 1,568 of the 1,582 remaining leaks. Opening `ชื่อของ/ชื่อใน` wide enough to catch it flagged 14 of 15 real customer questions, and a `ชื่อเล่น`-only version still swallowed 8 of 15; a false positive here holds a finished clip, which cost three weeks of silence in September. **A name that is literally a particle** ("ชื่อของลูกค้าคือ นะ ครับ") is silenced by the slot rule, accepted because a person called นะ or คะ is not a real case while เจ้าหนี้, มะนาว and คะนอง are — and each of those was silenced in measurement by a particle list that was not anchored to a space.

**A `คุณ` name longer than five code points** is not detected at all: `KHUN_NAME_RE` bounds its slot at five, and Thai vowels and tone marks each count, so สมหญิง (6), ธนวัฒน์ (7) and ประสิทธิ์ (9) all exceed it. The bound is what keeps คุณ — the everyday word for "you" — from swallowing clauses, so raising it means re-measuring `KHUN_STOPLIST` against real questions; the security gate confirmed the behaviour is identical on main, so it is a standing gap rather than anything this branch changed.

The cost of all this lands on the spaced introduction, and the earlier claim that "the question survives" was too broad: it survives when a particle follows the name ("ชื่อของสามี สมชาย ครับ ช่วยดูให้ได้ไหม" keeps its question), but with no particle to stop it the gap runs its full width and the whole message becomes one `[ชื่อ]`. FAQ mining then has a row it cannot use. That is fail-closed rather than a leak, and it is the next thing to improve here.

What is still true of the deterministic gate in general: a false positive costs a piece waiting in the review queue, a false negative costs a real name reaching a public post. That is why every trade above is recorded rather than smoothed over, and why the AI pass may only ever make a verdict stricter.

**Thai word boundaries (2026-09-15).** Clearing the review backlog surfaced a scanner bug: the name rules matched inside other words, because Thai is written without spaces. เชื่อ (believe) contains ชื่อ (name), so "ความน่าเชื่อถือ" and "ความเชื่อมโยง" were reported as a person's name, and ทนายความ (lawyer) matched the title นาย — on the deterministic gate that decides whether a piece may be published. 129 knowledge rows in one review run were held for this reason alone, and every generated piece using those very ordinary words was pushed to manual review. The cue rule now refuses to match after a Thai leading vowel, and the title rule works at the level of words rather than positions — nothing is blocked *before* a title at all; what it refuses is the compounds that never introduce a person (ทนายความ, นายหน้า, นายจ้าง, นางแบบ, นายกรัฐมนตรี…), each listed under the title that owns it. Three wrong shapes came first, each caught by a gate and each worse than the bug: a lookbehind on any Thai letter meant a title only counted at the start of a field ("ลูกค้าพบนายสมชาย" stopped being detected at all); a shared exclusion list meant นางเอก/นางฟ้า silenced นายเอกชัย/นายฟ้าลิขิต; and writing the นายก exclusion as a letter class (`ก[ก-๙]`) silenced every name starting with ก — นายกิตติ, นายกมล, นายกานต์. Exclusions now belong to the title that owns them and are spelled as whole compounds (นายกรัฐมนตรี, นายกสมาคม, นายกเทศมนตรี…), ทนายความ is excluded by name rather than by blocking ท- (which had swallowed ทนายสมชาย), and the tests put names mid-sentence. The lesson is in the shape of the mistakes: every attempt to exclude a false positive by position or by letter took real names with it. `ชื่อ<particle> … คือ|ว่า|<space> <name>` gets its own rule so excluding those particles from the cue does not lose a real introduction, and its gap refuses to contain คือ/ว่า so a rejected "คือการ…" cannot slide to the next ว่า.

`scripts/studio-approve-knowledge.ts [--dry-run] [--user <uuid>] [--limit N] [--category a,b]` approves canonical rows (tag `consolidated`) for AI content use. It only touches rows that are still active, unapproved, not `restricted`, carry neither review flag (`ต้องตรวจ privacy`, `ต้องยืนยัน`), and pass a **fresh** deterministic scrub with no high/medium finding — anything else is counted and left for the owner. First run 2026-09-10: 919 canonical rows unapproved → 388 approved (services 114, investigator_knowledge 114, cases 78, gps 54, osint 28), 531 skipped as flagged, 0 caught by the fresh scan. Case lessons stay `confidential`; retrieval excludes only `restricted`, so they are usable — un-approve individually in the UI if that is not wanted.

## 17. Motion hook — an 8 s generated clip as the first shot (2026-09-14)

**Why.** The owner asked what a moving clip would cost. Full motion is ฿115–490 per clip depending on the Veo tier, against ฿30–50 for the stills template; a motion *hook* (the first 8 s, where viewers decide to stay) is ฿22 on Veo 3.1 Lite 1080p, about ฿60–70 per finished clip. Measured 2026-09-14 from the pricing page: Lite $0.08/s at 1080p, Fast $0.12/s, standard $0.40/s.

**Two phases, because generation outlasts a function.** Veo takes minutes and Vercel allows 300 s, so nothing waits:
1. `generateMotionHook` (server action, admin + published lock + the media rate limit) builds the prompt server-side from the plan's first shot, scans it for identifiers, calls `predictLongRunning`, and stores a `pending` asset (`kind broll`, `meta.target.kind = "hook_motion"`, `meta.veo.operation`).
2. Cron `/api/cron/studio-motion-hook` every 5 min (`finishPendingHookMotions`) polls each pending asset, downloads the sample, uploads it to `studio-media` and flips the asset to `ready`. A network blip leaves the asset pending and retries next sweep; past `MOTION_TIMEOUT_MS` (20 min) or on a safety refusal it is marked `failed` with the reason.

**Spend guards.** Admin + the published-content lock + the shared media rate limit (10 per 5 min, counted across images, TTS and motion hooks). The asset row is claimed *before* the provider is called, and migration 0123 adds a partial unique index (one `pending` hook per master), so two concurrent clicks cannot both pay; a failed start frees the slot and the quota row is written the moment the spend happens (`purpose video_hook`; the cron's completion row is `video_hook_finish` so nothing is charged twice).

**Render.** `render.ts` looks for a ready motion hook (unless `job.params.motion_hook === false`), downloads it and sets `videoPath` on the first shot; `buildFfmpegArgs` then feeds it as a real clip — no `-loop`, no zoompan, `tpad` holds the last frame if the narration outlasts the 8 s, and the clip's own audio is never mapped. Nothing here can block a render: a hook that is still generating or failed simply leaves the still in place, and the asset records `meta.motion_hook`.

**Prompt safety.** `MOTION_SAFETY_NEGATIVES` bans speech, music and any on-screen text (we burn our own subtitles), plus faces, plates, documents, logos and banknotes — Thai notes carry the King's portrait, which this brand does not put in an advert.

**Model.** `media_prefs.video_model`, default `veo-3.1-lite-generate-preview`. Autopilot does not use motion hooks yet; that is a separate change.

## 16. Autopilot — Phase 4: scheduled end-to-end production + posting (migration 0121)

**Goal.** Owner decision 2026-09-10: the studio should produce and post by itself on a schedule, using the **template video** (stills + Thai voice-over), not Veo. One autopilot run = one finished post.

**Pipeline (one cron run, `maxDuration` 300 s).** pick pillar (largest gap vs the mix targets, or fixed) → take the oldest `saved` idea for that pillar, else generate ideas from a brief built from the top **owner-approved** customer questions (fenced as untrusted reference text — customer-authored) and save them → create the master → `generateScript` → `generateCreativePlan` → cover image (+ the storyteller presenter when the format asks for one, + one scene image per shot until the run's `images_per_run` ceiling is reached) → template video render (reuse `runRenderJob`) → privacy check (deterministic **and** AI, because no human sees it) → approve → publish to the configured platforms → LINE notification with the links. Every step writes `studio_autopilot_runs.step/progress`; a failure stops the run, records the reason and pings LINE.

**Identity.** The cron has no session, so the run resolves the oldest `admin` profile and acts as that person: every uuid column, per-user quota and audit row is attributable, and the run refuses to start when no admin exists.

**One image per shot (2026-09-14).** The owner's first sample clip reused two images across six spoken lines, so a line about a car leaving at odd hours sat under a photo of a phone on a table. The autopilot now generates one scene image per shot, with `images_per_run` acting as the cost ceiling for the whole run (cover and presenter included; default 7, max 10, ฿1.5 an image (`IMAGE_COST_THB`)). The ceiling is honoured literally: a storyteller run with `images_per_run: 1` has no room for the presenter, so it skips it and renders as a template clip (`stats.format_fallback: "image_cap"`). The scene prompt also carries the line the viewer hears over that shot, and the creative-plan prompt requires each shot's visual to show its own line with no two shots sharing a visual idea.

**Publishing sweep (2026-09-14).** The first real run (14 Sep 02:10) produced everything and then stopped at `timeout` — 264 s of the 300 s limit went to script (56 s), plan (56 s), images (8 s), render (109 s, template v2 is about twice as slow as v1) and the privacy pass (18 s), leaving nothing for the post. The run is right to stop: it never starts a public post it may not live long enough to record. So publishing is now its own step — cron `/api/cron/studio-autopilot-publish` every 15 min (`publishPendingAutopilotRuns`) posts the pieces those runs left behind, through the same `publishMaster` path. It only touches a run that stopped at `timeout_before_publish` — a reason used at the publish step alone, so a run that ran out of time earlier is never swept — is still unpublished, is under a day old, and whose master is still `approved`/`scheduled`, has a ready video and no social post yet; it respects `enabled`, `auto_publish` and `platforms` as they are *now*, claims the run first (`stopped_at = 'publishing'`, compare-and-set) so two fires cannot post the same piece, skips a master whose `scheduled_at` is still in the future (the owner's chosen time wins), closes the run as `done` with `stats.recovered`, audits `STUDIO_SOCIAL_POST`, and LINE-notifies either way.

**Hard stops (never bypassed).** The AI privacy pass must actually run — a degraded (deterministic-only) verdict stops the run, because the regex scan cannot see names, places or case-identifying detail and nobody reads the output. A `blocked` privacy result stops the run before approval — nothing is published and the master stays `review` for the owner. `review_required` follows `autopilot.publish_on_review_required` (default **false** → stops and asks) **and** `approval_rules.allow_override`; publishing one is recorded as an `override_privacy` review, not a plain approve. A privacy-check or review row that fails to store stops the run. Unsupported fact claims from the script generator are recorded as usual; when any claim is `unsupported` the run stops unless `allow_unsupported_claims` is on. Platform posting reuses Phase 2 in full (linked-account check, per-platform captions re-scrubbed, duplicate guard, rate limit).

**Settings** (`studio_settings.autopilot`): `enabled`, `days` (0–6, Bangkok), `platforms`, `pillar_mode` (`rotate|fixed`) + `pillar`, `target_seconds`, `images_per_run`, `auto_publish` (false = produce and leave in review), `publish_on_review_required`, `allow_unsupported_claims`, `max_runs_per_week`. Cron `/api/cron/studio-autopilot` fires daily 02:10 Bangkok (`10 19 * * *` UTC) and exits immediately when disabled, off-day, or the weekly cap is reached.

**Time budget.** The cron route gets 300 s; a measured live run (6 shots, 2 images, 47 s clip) took **207 s** — script 34 s, plan 49 s, images 25 s, render 65 s, AI privacy 11 s. The plan is therefore trimmed to 8 shots, optional scene images are skipped within 150 s of the budget, and the run refuses to start the render (110 s) or a public post (45 s) when too little time remains. A run the platform killed is reaped after 10 minutes so the one-running-row index cannot deadlock the schedule, and that skip is audited.

Text too long to flatten gets the other defence instead — an unguessable boundary (`prompts/envelope.ts`): `envelopeTag()` is 8 random bytes per request, `dataEnvelope()` wraps the body in `<<LABEL:tag>> … <<END:tag>>` and strips any copy of the tag out of the body first, and `ENVELOPE_FENCE` says once, above it, that nothing inside is an instruction.
